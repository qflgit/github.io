vLLM 推理引擎详解：PagedAttention、连续批处理与投机解码

一、概述

vLLM 是由加州大学伯克利分校团队于 2023 年开源的高性能大语言模型推理框架，现已成为 Mistral、Qwen、Llama、DeepSeek 等主流模型最常用的推理后端之一。vLLM 的核心目标是通过底层架构创新解决 LLM 推理中的两大瓶颈——显存管理效率和GPU 计算利用率，从而在保证低延迟的同时实现高吞吐量。其三大核心技术 PagedAttention、连续批处理（Continuous Batching）和投机解码（Speculative Decoding）构成了现代 LLM 推理优化的基石。

二、LLM 推理的挑战

2.1 自回归生成的计算特性

大语言模型的文本生成是一个自回归、串行的过程：每步只生成一个 token，下一个 token 严格依赖所有已生成的历史 token。这种特性导致两个核心问题：

问题一：KV Cache 显存爆炸

为了避免重复计算历史 token 的注意力，现代推理系统会缓存每个 token 的 Key（K）和 Value（V）向量，即 KV Cache：

​x
KV_Cache_Size = 2 (K和V) × num_layers × num_heads × head_dim × seq_len × batch_size × dtype_size


示例：LLaMA-13B、seq_len=2048、batch=16、FP16
KV Cache ≈ 26 GB —— 比模型权重（26 GB）还大

显存利用率往往不是被模型权重撑爆的，而是被 KV Cache 撑爆的。

问题二：静态批处理的计算浪费

传统静态批处理必须等批次内所有请求都完成后才能进入下一轮。由于请求长度差异巨大，短请求被迫等待长请求，GPU 在部分序列完成后出现空闲，计算资源严重浪费。

2.2 传统框架的局限

三、PagedAttention：显存管理的革命

3.1 核心思想

PagedAttention 借鉴操作系统虚拟内存的分页机制，将 KV Cache 划分为固定大小的块（block），通过块表（block table）实现逻辑连续、物理离散的动态内存管理。

3.2 技术原理

3.2.1 传统连续分配 vs PagedAttention

xxxxxxxxxx
传统连续分配:
序列 A: [token1][token2][token3][token4][token5]  预分配 2048 个位置
         └────────── 连续显存块 ──────────┘
         实际使用 5/2048 = 0.2% 利用率


PagedAttention:
序列 A 块表: [Block0][Block1][Block2]
              ↓      ↓      ↓
物理显存:    [B0]   [B5]   [B2]  ← 非连续，按需分配


Block 大小: 通常 16 个 token（可配置）

3.2.2 块表机制

xxxxxxxxxx
# 逻辑视角：每个序列维护一张块表
sequence_block_table = {
    'seq_A': [0, 5, 2],      # 逻辑块 0,1,2 映射到物理块 0,5,2
    'seq_B': [0, 5, 7],      # 与 seq_A 共享前两个块（前缀相同）
    'seq_C': [1, 3, 4, 6]    # 完全不同的物理块
}


# 物理块分配：由全局块分配器管理
# 空闲块池 → 按需分配 → 引用计数 → 回收复用

3.2.3 内存共享机制

xxxxxxxxxx
前缀共享（Prefix Sharing）:
System Prompt: "You are a helpful assistant."
    ↓
请求 A: "Explain quantum computing" → 共享前缀块
请求 B: "Write a poem about AI"    → 共享前缀块
请求 C: "You are a coding expert." → 不同前缀，独立块


效果：相同前缀的 KV Cache 只计算一次，多请求共享

Copy-on-Write（写时复制）：

  • 多个序列共享同一块时，引用计数 > 1

  • 当某序列需要修改该块（生成新 token），触发复制

  • 新块分配给该序列，原块引用计数减 1

四、连续批处理（Continuous Batching）

4.1 核心思想

连续批处理（也称迭代级调度、动态批处理）将批处理粒度从"请求级"降到"token 级"——GPU 每生成一个 token，就重新调度批次，让新请求随时加入、已完成请求立即退出，GPU 始终保持高利用率。

4.2 对比：静态批处理 vs 连续批处理

4.2.1 静态批处理

xxxxxxxxxx
批次 1: [ReqA(短), ReqB(长), ReqC(中)]
  Step 1: 所有请求生成 1 token
  Step 2: 所有请求生成 1 token
  ...
  Step N: ReqA 完成，但 ReqB 和 ReqC 仍在运行
  Step N+1: ReqA 空转（等待其他请求）
  ...
  Step M: 所有请求完成 → 才能启动批次 2


问题: ReqA 完成后 GPU 空转，ReqB 阻塞后续批次

4.2.2 连续批处理

xxxxxxxxxx
生成循环（每步迭代）:
  Step 1: [ReqA, ReqB, ReqC] 各生成 1 token
  Step 2: [ReqA, ReqB, ReqC] 各生成 1 token
  Step 3: [ReqA(完成→退出), ReqB, ReqC] + [ReqD(新加入)]
  Step 4: [ReqB, ReqC, ReqD] 各生成 1 token
  Step 5: [ReqB, ReqC(完成→退出), ReqD] + [ReqE, ReqF(新加入)]
  ...


特点:
  - 每步都有新请求加入
  - 每步都有完成请求退出
  - GPU 始终处理活跃请求，无空转

4.3 与 PagedAttention 的协同

xxxxxxxxxx
连续批处理 + PagedAttention:
  1. 调度器每步检查请求队列
  2. 新请求加入：分配空闲块（PagedAttention 动态分配）
  3. 活跃请求生成：使用已有块表
  4. 完成请求退出：释放块（引用计数减 1，归零时回收）
  5. 重复步骤 1-4


关键：PagedAttention 的灵活块管理使连续批处理成为可能
      传统连续分配无法支持请求的动态加入/退出

五、投机解码（Speculative Decoding）

5.1 核心思想

投机解码利用 LLM 生成中的局部可预测性：用一个小模型（草稿模型）快速"猜测"接下来几个 token，然后由大模型（目标模型）一次性验证这些猜测。如果猜测正确，大模型一步生成多个 token；如果错误，回退到正确位置继续。

5.2 工作流程

xxxxxxxxxx
标准解码（每步 1 token）:
  大模型: "The PagedAttention" → "algorithm"
  大模型: "The PagedAttention algorithm" → "is"
  大模型: "The PagedAttention algorithm is" → "inspired"
  ... 每步 1 个 token，N 步生成 N 个 token


投机解码（每步最多 K+1 token）:
  草稿模型（小模型）:
    "The PagedAttention" → "algorithm is inspired by"
    草稿生成 K=3 个候选 token: ["algorithm", "is", "inspired"]


  大模型（目标模型）:
    输入: "The PagedAttention" + ["algorithm", "is", "inspired", "by"]
    并行验证所有候选位置


    验证结果:
      位置 1: "algorithm" ✓ 正确
      位置 2: "is" ✓ 正确
      位置 3: "inspired" ✗ 错误（大模型预测为 "based"）


    接受: ["algorithm", "is"]
    拒绝: "inspired" 及之后
    新起点: "The PagedAttention algorithm is" + "based"


  本步实际生成: 2 个 token（"algorithm", "is"）+ 修正 1 个 token（"based"）
  等效: 每步生成 2-3 个 token，速度提升 2-3 倍

5.3 数学原理

xxxxxxxxxx
设草稿模型接受率为 α（猜测正确的概率）
设每步草稿生成 K 个 token


期望接受 token 数: E = α × K
期望验证步数: 1（大模型始终只运行 1 步）


加速比 ≈ (1 + E) / 1 = 1 + α × K


当 α = 0.8, K = 5 时:
  加速比 ≈ 1 + 0.8 × 5 = 5 倍（理论上限）


实际考虑:
  - 草稿模型开销
  - 内存带宽限制
  - 实际加速: 1.5-3 倍

六、其他关键优化技术

6.1 分块预填充（Chunked Prefill）

问题：长提示（如 32K token）的预填充阶段一次性占用大量 GPU 计算，阻塞其他短请求的解码。

解决方案：将长预填充拆分为多个小块，在块之间穿插其他请求的解码步骤。

xxxxxxxxxx
无分块预填充:
  长请求: [Prefill 32K] → [Decode] → [Decode] ...
  短请求: 等待 32K 预填充完成 → [Decode] → ...
  TTFT p95: 2,800 ms（32K 输入时）


分块预填充:
  长请求: [Prefill 4K] → [Decode 短请求] → [Prefill 4K] → [Decode 短请求] ...
  短请求: [Decode] → [Decode] → ...（不受长请求阻塞）
  TTFT p95: 890 ms（68% 改善）

6.2 前缀缓存（Prefix Caching）

自动识别多个请求中的相同前缀（如 System Prompt、工具说明、少样本示例），复用对应的 KV Cache，避免重复计算。

xxxxxxxxxx
请求 A: System Prompt + "Explain quantum computing"
请求 B: System Prompt + "Write a poem about AI"
请求 C: System Prompt + "Debug this Python code"


前缀缓存:
  System Prompt 的 KV Cache 只计算一次
  三个请求共享该前缀块
  后续请求直接使用缓存，Prefill 时间几乎为 0

九、总结

vLLM 的成功证明了跨领域知识迁移的力量——将操作系统的虚拟内存思想引入 LLM 推理领域，彻底解决了 KV Cache 的内存管理难题。在 2026 年的今天，LLM 推理优化已形成一套完整的技术体系：PagedAttention 解决内存效率，连续批处理提升 GPU 利用率，投机解码加速 token 生成，分块预填充平衡延迟与吞吐。这些技术的叠加效应使得 LLM 推理的成本持续下降，为 AI 应用的大规模部署扫清了障碍。理解这些底层原理，将帮助开发者构建更高效、更经济的 AI 系统。
