TensorRT-LLM 优化详解：内核融合、FP8 量化与多 GPU 并行

一、概述

TensorRT-LLM 是 NVIDIA 官方推出的高性能大语言模型推理引擎，基于 TensorRT 编译框架构建，通过底层 CUDA 内核优化、量化压缩和多 GPU 并行策略，将 LLM 推理性能推向硬件理论极限。与 vLLM 等运行时优化框架不同，TensorRT-LLM 采用编译时优化策略——将 PyTorch 模型离线编译为高度优化的 TensorRT 引擎，通过内核融合、层优化和硬件特性定制实现极致性能。在 H100 GPU 上，TensorRT-LLM 运行 Llama 3 70B 的吞吐量可达 10,000+ tokens/秒，相比原生 PyTorch 提升 4 倍，相比 vLLM 提升 20-40%。

2.1 编译优化范式

PyTorch 模型（HuggingFace 格式）
    ↓

    ↓

    ↓

    ├── 图优化（层融合、常量折叠）

    ├── 内存优化（显存分配策略）
    └── 并行策略配置（TP/PP）
    ↓
TensorRT 引擎（.plan 文件）
    ↓
运行时推理（C++/Python API）

关键特性：

  • 硬件专属：引擎与 GPU 架构绑定（A100 引擎无法在 H100 上运行）

  • 编译耗时：引擎构建通常需 20-60 分钟（取决于模型大小和 GPU）

  • 冷启动：首次推理需内核预热（10-20 个 dummy 请求）

  • 不可移植：不同 GPU 类型需分别构建引擎

三、内核融合（Kernel Fusion）

3.1 核心思想

内核融合将多个独立的 CUDA 操作合并为单个优化内核，减少 GPU 内核启动开销和内存访问次数。Transformer 的层标准化、矩阵乘法、偏置加法和激活函数等操作，在传统实现中需要多次读写显存，而融合后只需一次读写。

3.2 典型融合模式

​x
融合前（独立内核）：
  输入 X → [LayerNorm] → Y → [MatMul] → Z → [BiasAdd] → W → [GELU] → 输出
  显存访问: 6 次（每层操作读写一次）
  内核启动: 4 次


融合后（单一内核）：
  输入 X → [Fused MLP Block] → 输出
  显存访问: 2 次（仅输入和输出）
  内核启动: 1 次


中间结果全部保存在寄存器/共享内存中，无需写回全局显存

四、FP8 量化

4.1 为什么 FP8

FP8（8-bit 浮点）是 NVIDIA Hopper/Blackwell 架构的原生支持格式，相比 FP16 提供：

  • 显存减半：权重和激活值从 2 bytes 降至 1 byte

  • 计算加速：Tensor Core FP8 运算速度是 FP16 的 2 倍

  • 精度可控：通过缩放因子（Scaling Factor）保持数值稳定性

4.2 FP8 格式

xxxxxxxxxx
FP8 两种格式（NVIDIA 定义）：


E4M3（4 位指数 + 3 位尾数）：
  - 范围: ±448.0
  - 用途: 前向激活、权重


E5M2（5 位指数 + 2 位尾数）：
  - 范围: ±57344.0
  - 用途: 梯度、KV Cache


动态范围选择：
  - 每层独立缩放因子
  - 校准过程确定最优缩放

五、多 GPU 并行策略

5.1 张量并行（Tensor Parallelism, TP）

5.1.1 原理

将模型层内的权重矩阵按行或列切分到多个 GPU，每个 GPU 负责部分计算：

xxxxxxxxxx
线性层: Y = X · W


TP 切分（按列切分）:
  GPU0: Y0 = X · W[:, 0:N/2]
  GPU1: Y1 = X · W[:, N/2:N]


结果: Y = [Y0, Y1]（拼接）


通信: All-Gather（仅输出时通信）

5.1.2 配置

xxxxxxxxxx
# 4 GPU 张量并行
trtllm-build     --checkpoint_dir ./ckpt     --output_dir ./engine_tp4     --tp_size 4     --pp_size 1


# 运行时
python3 run.py     --engine_dir ./engine_tp4     --tokenizer_dir ./hf_model     --input_text "Explain quantum computing"     --max_output_len 256

5.2 流水线并行（Pipeline Parallelism, PP）

5.2.1 原理

将模型按层切分到多个 GPU，每个 GPU 负责连续的若干层：

xxxxxxxxxx
模型层: [Layer0-7][Layer8-15][Layer16-23][Layer24-31]


GPU0: Layer0-7
GPU1: Layer8-15
GPU2: Layer16-23
GPU3: Layer24-31


前向传播: GPU0 → GPU1 → GPU2 → GPU3
反向传播: GPU3 → GPU2 → GPU1 → GPU0


通信: P2P 通信（层间传递激活值）

5.2.2 微批次（Micro-Batching）

xxxxxxxxxx
PP 微批次调度（4 个 GPU，4 个微批次）:


时间步  GPU0      GPU1      GPU2      GPU3
  1     批次1F    -         -         -
  2     批次2F    批次1F    -         -
  3     批次3F    批次2F    批次1F    -
  4     批次4F    批次3F    批次2F    批次1F
  5     批次1B    批次4F    批次3F    批次2F
  6     批次2B    批次1B    批次4F    批次3F
  7     批次3B    批次2B    批次1B    批次4F
  8     批次4B    批次3B    批次2B    批次1B


F: 前向, B: 反向
气泡: 空闲等待时间（通过微批次减少）

九、总结

TensorRT-LLM 代表了 LLM 推理优化的"编译器范式"——通过离线编译将模型转化为硬件专属的高度优化引擎，在牺牲一定灵活性的前提下实现极致性能。对于追求峰值吞吐量、稳定低延迟的生产级部署场景，TensorRT-LLM 配合 FP8 量化和多 GPU 并行，能够将 H100 的硬件潜力发挥到极致。理解其内核融合、量化策略和并行机制，是构建高性能 AI 推理基础设施的关键。
