1. 概述

文档分块(Chunking)是RAG系统的核心预处理步骤,将长文档切分为可管理的片段以便向量化存储和检索。分块策略的选择直接影响检索质量--研究表明,分块策略的差异可导致高达9%的召回率差距,且分块选择对检索质量的影响往往超过Embedding模型选择。

分块的核心矛盾在于:

  • 分块太大:包含无关噪音,稀释检索精度,且可能超出Embedding模型上下文限制

  • 分块太小:语义碎片化,丢失上下文,AI无法理解完整含义

  • 分块边界:在句子中间切断会导致语义断裂(如"不"和"准发放奖金"被切开)

2026年的最佳实践已从简单的固定长度分块演进为语义感知、层次化、上下文增强的综合策略体系。

2. 分块策略分类

2.1 固定长度分块

原理:按固定字符数或Token数切分文档,可设置重叠区域防止边界信息丢失。

实现:

​x
from langchain.text_splitter import CharacterTextSplitter


splitter = CharacterTextSplitter(
    chunk_size=512,        # 每块最大字符数
    chunk_overlap=50,      # 重叠字符数
    separator="\n"         # 分隔符
)
chunks = splitter.split_text(text)

优点:

  • 实现最简单,无需NLP依赖

  • 速度快,完全可预测

  • 适合同质性文档(日志、数据导出)

  • 快速原型阶段首选

缺点:

  • 容易在句子中间切断,语义断裂

  • 不考虑文档结构(表格跨块、段落被切)

  • 检索精度低,召回率差距可达9%

  • 重叠区域增加索引成本但收益有限

适用场景:

  • 内容结构简单均匀的文本

  • 快速原型验证

  • 对检索精度要求不高的场景

  • 日志、CSV等结构化数据

性能数据:

  • FloTorch基准测试准确率:67%(落后递归分块2个百分点)

  • 索引速度:最快(无NLP开销)

2.2 递归字符分块

原理:使用分隔符层级体系,优先在更自然的边界处切分。先尝试段落分隔(\n\n),若结果仍过大则尝试行分隔(\n),再尝试句子分隔(. ),最后尝试单词分隔(空格),字符级切分为最后手段。

实现:

xxxxxxxxxx
from langchain.text_splitter import RecursiveCharacterTextSplitter


splitter = RecursiveCharacterTextSplitter(
    chunk_size=512,
    chunk_overlap=50,
    length_function=len,
    separators=["\n\n", "\n", ". ", "! ", "? ", " ", ""]  # 优先级顺序
)
chunks = splitter.split_text(text)

Token精确版本:

xxxxxxxxxx
# 使用tiktoken进行token精确切分(推荐)
splitter = RecursiveCharacterTextSplitter.from_tiktoken_encoder(
    encoding_name="cl100k_base",  # GPT-4的tokenizer
    chunk_size=512,               # token数(非字符数)
    chunk_overlap=50
)

重要注意:LangChain的RecursiveCharacterTextSplitter默认按字符计数(length_function=len),而非token计数。512字符约等于128个token,这会静默低估实际token消耗。必须使用from_tiktoken_encoder()进行token精确切分。

优点:

  • 保留文档自然结构(段落、句子完整性)

  • 工程界公认的"瑞士军刀",最广泛使用的生产策略

  • 自适应降级策略:尽可能接近目标大小

  • 适合几乎所有通用RAG应用

缺点:

  • 对短文档可能过度切分(200字FAQ切成3个70字片段)

  • 对跨段落引用("如第3节所述")处理不佳

  • 无法识别主题转换边界

适用场景:

  • 文章、研究论文、文档等通用文本

  • 大多数生产RAG系统的默认选择

  • 混合格式文档

性能数据:

  • FloTorch基准测试准确率:69%(50篇学术论文,905,746 tokens)

  • 2026年2月厂商基准测试:7种策略中排名第一

  • 索引速度:4.82 MB/s(token-based)

2.3 语义分块

原理:基于Embedding相似度检测主题转换边界。将文档切分为句子,计算相邻句子间的语义相似度,在相似度低于阈值的位置切分。

实现:

xxxxxxxxxx
from chonkie import SemanticChunker
from sentence_transformers import SentenceTransformer


model = SentenceTransformer("sentence-transformers/all-MiniLM-L6-v2")


chunker = SemanticChunker(
    embedding_model=model,
    chunk_size=512,
    min_chunk_size=200,       # 防止过小碎片
    similarity_threshold=0.5  # 相似度阈值
)


chunks = chunker.chunk(text)

LlamaIndex语义双分块器:

xxxxxxxxxx
from llama_index.core.node_parser import SemanticDoubleMergingChunker


# 先按语义聚类,再合并相似相邻块避免过度碎片化
chunker = SemanticDoubleMergingChunker(
    buffer_size=1,
    breakpoint_percentile_threshold=80,
    embed_model=OpenAIEmbedding()
)

优点:

  • 每个块天然是完整语义单元

  • RAG准确率提升12-18%

  • 适合叙事内容、研究文档、支持文档

  • 块大小自适应内容密度

缺点:

  • 速度较慢:约0.33 MB/s(比token-based慢14倍)

  • 需要Embedding模型推理

  • 大规模语料库处理耗时(小时级 vs 分钟级)

  • 阈值调参敏感

适用场景:

  • 多主题混杂文档

  • 研究论文、支持文档

  • 当检索指标证明收益值得额外成本时

性能数据:

  • Chroma基准召回率:91.9%

  • 速度:0.33 MB/s(vs token-based的4.82 MB/s)

  • 准确率提升:12-18%(vs固定长度)

2.4 层次化分块

原理:维护两层(或多层)分块结构。小子块(128-256 tokens)用于精确检索,大父块(512-2048 tokens)用于生成上下文。检索时用小块定位,返回父块作为LLM输入。

实现(父子文档策略):

xxxxxxxxxx
class ParentChildChunker:
    def __init__(self, parent_chunk_size=1500, child_chunk_size=300):
        self.parent_splitter = RecursiveCharacterTextSplitter(
            chunk_size=parent_chunk_size,
            chunk_overlap=100
        )
        self.child_splitter = RecursiveCharacterTextSplitter(
            chunk_size=child_chunk_size,
            chunk_overlap=30
        )


    def create_chunks(self, document, doc_id):
        parent_chunks = self.parent_splitter.split_text(document)
        parents = []
        children = []
        for p_idx, parent in enumerate(parent_chunks):
            parent_id = f"{doc_id}_p{p_idx}"
            parents.append({
                "id": parent_id,
                "content": parent,
                "type": "parent"
            })
            child_chunks = self.child_splitter.split_text(parent)
            for c_idx, child in enumerate(child_chunks):
                children.append({
                    "id": f"{parent_id}_c{c_idx}",
                    "parent_id": parent_id,
                    "content": child,
                    "type": "child"
                })
        return {"parents": parents, "children": children}

检索流程:

xxxxxxxxxx
class ParentChildRAG:
    def retrieve(self, query, top_k=5):
        # 1. 检索子文档(精确匹配)
        child_results = vector_store.search(query, top_k=top_k)
        # 2. 获取对应父文档ID(去重)
        parent_ids = list(set([
            r["metadata"]["parent_id"] for r in child_results
        ]))
        # 3. 返回完整父文档作为上下文
        return [parent_store[pid] for pid in parent_ids]

句子窗口变体:

  • 检索句子级小块

  • 返回该句子前后3个句子的窗口作为上下文

  • 无需维护层次索引,实现更简单

优点:

  • 解决精度与上下文的根本矛盾

  • 小子块精确检索,大父块丰富生成上下文

  • 避免"孤立片段"幻觉模式

  • 2025-2026年最广泛采用的生产模式

  • ARAGOG 2024基准测试中 consistently 排名前列

缺点:

  • 需要维护两层索引(子块检索 + 父块存储)

  • 文档更新时需刷新两层

  • 父块大小需根据内容类型调优

适用场景:

  • 任何需要同时保证检索精度和生成质量的RAG管道

  • 生产部署的默认模式

  • 长文档检索

性能数据:

  • 检索精度提升25%(配合摘要索引)

  • 解决"总是从第一块返回响应,忽略第二、三块"的常见故障

2.5 Late Chunking

原理:颠覆传统"先分块再嵌入"的顺序,先嵌入完整文档(保留全局上下文),再对嵌入结果进行分块。每个块的嵌入携带周围文档的上下文感知,包括代词、交叉引用和标题信息。

实现:

xxxxxxxxxx
from chonkie import LateChunker
from sentence_transformers import SentenceTransformer


# 必须使用长上下文Embedding模型
model = SentenceTransformer("jinaai/jina-embeddings-v3", trust_remote_code=True)


chunker = LateChunker(
    embedding_model=model,
    chunk_size=512,
)


chunks = chunker.chunk(text)
# 每个chunk.embedding反映完整文档上下文

优点:

  • 保留跨段落引用和代词指代

  • 解决"如第3节所述"类引用丢失问题

  • 适合技术手册、法律文档、学术论文

  • BEIR基准增益随文档长度增长而增长

缺点:

  • 需要长上下文Embedding模型(支持8192+ tokens)

  • 文档超过模型上下文窗口时无法使用

  • 对简单散文改进有限

适用场景:

  • 密集交叉引用的文档

  • 技术手册、法律文档

  • 学术论文("如前文所述"类引用多)

2.6 Agentic分块

原理:使用LLM分析文档结构并决定切分位置。LLM读取每个部分,判断最佳切分点。

实现:

xxxxxxxxxx
# 伪代码示例
class AgenticChunker:
    def chunk(self, document):
        # 使用LLM分析文档结构
        analysis = llm.analyze_structure(document)
        # LLM返回切分建议
        split_points = analysis["split_points"]
        # 按建议切分
        chunks = []
        start = 0
        for point in split_points:
            chunks.append(document[start:point])
            start = point
        chunks.append(document[start:])
        return chunks

优点:

  • 最佳边界质量

  • 最高检索精度

  • 适合高价值、低容量文档

缺点:

  • 索引成本最高(10-50倍于固定长度)

  • 每文档需要LLM调用

  • 速度慢,不适合大规模语料

适用场景:

  • 高价值、精心策划的语料库

  • 法律合同、金融报告

  • 文档量低但质量要求极高的场景

6. 上下文增强技术

6.1 Contextual Retrieval(Anthropic 2025)

原理:在分块前先用LLM为每个chunk生成上下文描述,解决孤立片段的语义丢失问题。

示例:

xxxxxxxxxx
原始chunk:
"公司的Q3净利润为1.2亿元,同比增长35%。"


增强后chunk:
"这段内容来自XX公司2025年Q3财报(2025-10-30发布)。
公司的Q3净利润为1.2亿元,同比增长35%。"

效果:

  • 召回失败率降低约49%

  • 配合重排序器可降低67%

  • 显著提升长文档中的细粒度检索精度

实现:

xxxxxxxxxx
class ContextualRetrieval:
    def __init__(self, llm, embedding_model):
        self.llm = llm
        self.embedding_model = embedding_model


    def add_contextual_headers(self, chunks, document_title):
        enhanced_chunks = []
        for chunk in chunks:
            prompt = f"""
            文档标题:{document_title}
            当前片段:{chunk[:200]}...


            请用1-2句话说明这个片段在文档中的位置和上下文。
            只返回描述,不要其他内容。
            """
            context = self.llm.generate(prompt).strip()
            enhanced_chunk = f"{context}\n\n{chunk}"
            enhanced_chunks.append(enhanced_chunk)
        return enhanced_chunks

6.2 分层索引(摘要+全文)

原理:建立两层索引:

  • 摘要索引:每个文档/分块的AI生成摘要,用于粗粒度定位

  • 全文索引:原始文本的向量化存储,用于精确定位

检索流程:

  1. 查询摘要索引,定位相关文档

  2. 在相关文档内查询全文索引,精确定位段落

  3. 检索精度提升25%

6.3 元数据增强

原理:使用LLM动态生成有意义的元数据,提升语义表示和检索精度。

元数据类型:

  • 标题、摘要、关键词

  • 时间戳、作者、分类

  • 章节路径、文档层级

效果:

  • 递归分块 + TF-IDF加权嵌入:82.5%精度

  • 简单分块 + 前缀融合:NDCG 0.813(最强排序质量)

  • P95延迟保持在30ms以内

7.2 渐进式优化路径

第一步:递归512-token分块(token精确计数)

  • 使用RecursiveCharacterTextSplitter.from_tiktoken_encoder()

  • 跳过重叠作为默认设置

  • 在代表性查询集上测量检索质量

第二步:按查询类型匹配块大小

  • 事实查找:64-256 tokens

  • 分析推理:512-1024+ tokens

  • 混合流量:按查询类别分段而非统一大小

第三步:当指标证明收益时升级

  • 语义分块:~14倍更慢,仅当RAGAS显示召回率或精度增益值得额外成本

  • 层次化分块:增加索引复杂度,适合生产环境

第四步:高价值语料库添加上下文增强

  • Contextual Retrieval:召回失败率降低49%

  • Late Chunking:适合密集交叉引用文档

8. 应用场景分析

8.1 企业知识库

需求:混合文档类型、多主题、高召回率 推荐策略:层次化分块(父子文档)+ 语义分块 配置:

  • 子块:256 tokens(精确检索)

  • 父块:1024 tokens(生成上下文)

  • 添加Contextual Retrieval增强

8.2 法律文档检索

需求:条款完整性、高精度、边界敏感 推荐策略:Agentic分块或自适应边界感知 配置:

  • 按条款/段落切分

  • 15-20%重叠确保条款不被切断

def get_chunker(strategy, chunk_size=512, overlap=50):
    if strategy == "fixed":
        return CharacterTextSplitter(
            chunk_size=chunk_size,
            chunk_overlap=overlap,
            separator="\n"
        )
    elif strategy == "recursive":
        return RecursiveCharacterTextSplitter.from_tiktoken_encoder(
            encoding_name="cl100k_base",
            chunk_size=chunk_size,
            chunk_overlap=overlap
        )
    elif strategy == "sentence":
        return SentenceSplitter(
            chunk_size=chunk_size,
            chunk_overlap=overlap,
        )
    elif strategy == "semantic":
        from sentence_transformers import SentenceTransformer
        model = SentenceTransformer("sentence-transformers/all-MiniLM-L6-v2")
        return SemanticChunker(
            embedding_model=model,
            chunk_size=chunk_size,
            min_chunk_size=200,
            similarity_threshold=0.5,
        )
    elif strategy == "late":
        from sentence_transformers import SentenceTransformer
        model = SentenceTransformer("jinaai/jina-embeddings-v3", trust_remote_code=True)
        return LateChunker(
            embedding_model=model,
            chunk_size=chunk_size,
        )
    else:
        raise ValueError(f"Unknown strategy: {strategy}")


def chunk_document(text, strategy, chunk_size=512, overlap=50):
    chunker = get_chunker(strategy, chunk_size, overlap)
    if strategy == "sentence":
        doc = Document(text=text)
        nodes = chunker.get_nodes_from_documents([doc])
        return [n.text for n in nodes]
    elif strategy in ["semantic", "late"]:
        return [c.text for c in chunker.chunk(text)]
    else:
        return chunker.split_text(text)

from langchain_text_splitters import RecursiveCharacterTextSplitter


class HierarchicalChunker:
    def __init__(self, parent_chunk_size=1500, child_chunk_size=300):
        self.parent_splitter = RecursiveCharacterTextSplitter.from_tiktoken_encoder(
            chunk_size=parent_chunk_size,
            chunk_overlap=100
        )
        self.child_splitter = RecursiveCharacterTextSplitter.from_tiktoken_encoder(
            chunk_size=child_chunk_size,
            chunk_overlap=30
        )


    def create_chunks(self, document, doc_id):
        parent_chunks = self.parent_splitter.split_text(document)
        parents = []
        children = []
        for p_idx, parent in enumerate(parent_chunks):
            parent_id = f"{doc_id}_p{p_idx}"
            parents.append({
                "id": parent_id,
                "content": parent,
                "type": "parent"
            })
            child_chunks = self.child_splitter.split_text(parent)
            for c_idx, child in enumerate(child_chunks):
                children.append({
                    "id": f"{parent_id}_c{c_idx}",
                    "parent_id": parent_id,
                    "content": child,
                    "type": "child"
                })
        return {"parents": parents, "children": children}


class HierarchicalRAG:
    def __init__(self, vector_store, parent_store):
        self.vector_store = vector_store
        self.parent_store = parent_store


    def index_document(self, document, doc_id):
        chunker = HierarchicalChunker()
        chunks = chunker.create_chunks(document, doc_id)
        for parent in chunks["parents"]:
            self.parent_store[parent["id"]] = parent
        for child in chunks["children"]:
            self.vector_store.add(
                id=child["id"],
                text=child["content"],
                metadata=child["metadata"]
            )


    def retrieve(self, query, top_k=5):
        child_results = self.vector_store.search(query, top_k=top_k)
        parent_ids = list(set([
            r["metadata"]["parent_id"] for r in child_results
        ]))
        contexts = []
        for pid in parent_ids:
            if pid in self.parent_store:
                parent = self.parent_store[pid]
                contexts.append({
                    "content": parent["content"],
                    "metadata": parent["metadata"]
                })
        return contexts

    def add_contextual_headers(self, chunks, document_title):

            文档标题:{document_title}
            当前片段:{chunk[:200]}...


            请用1-2句话说明这个片段在文档中的位置和上下文。

            """
            context = self.llm.generate(prompt).strip()
            enhanced_chunk = f"{context}\n\n{chunk}"
            enhanced_chunks.append(enhanced_chunk)
        return enhanced_chunks

10. 发展趋势

10.1 从固定大小到语义感知

2026年的主流趋势是从固定长度分块转向语义感知分块:

  • 语义分块准确率提升12-18%

  • 层次化分块成为生产默认

  • 上下文增强(Contextual Retrieval)降低召回失败率49%

10.2 动态查询感知分块

根据查询模式动态调整分块大小:

  • 事实查找:小尺寸(64-256 tokens)

  • 分析推理:大尺寸(512-1024+ tokens)

  • 按查询类别分段而非统一大小

10.3 多模态分块

将图像、表格、文本统一分块:

  • 使用LLM生成非文本元素的文本摘要

  • 统一向量化存储

  • 跨模态检索

10.4 神经分块模型

专用神经网络预测最优分块边界:

  • 平衡语义连贯性和块长度

  • 优于基于规则的方法

  • 2026年仍处于研究阶段

10.5 自进化分块

基于用户反馈自动优化分块策略:

  • 检索失败分析 -> 调整分块参数

  • A/B测试不同分块策略

  • 持续监控和迭代

10.6 与Embedding模型协同优化

分块策略与Embedding模型联合优化:

  • Late Chunking需要长上下文Embedding模型

  • 分块大小影响Embedding质量

  • 端到端联合训练

总结

文档分块是RAG系统中最被低估但影响最大的优化杠杆。2026年的最佳实践可总结为:

核心原则:

  1. 先测量,再优化:在代表性查询集上测试不同策略,用数据驱动决策

  2. 从简单开始:递归512-token分块是实用的默认起点

  3. 按查询类型匹配:事实查找用小尺寸,分析推理用大尺寸

  4. 上下文为王:层次化分块和上下文增强解决精度与上下文的矛盾

策略选择:

  • 快速原型:递归字符分块(512 tokens)

  • 生产默认:层次化分块(父子文档)

  • 高精度需求:语义分块 + 层次化

  • 交叉引用密集:Late Chunking

  • 高价值低容量:Agentic分块

  • 短文档:不分块或句子级

关键数据:

  • 分块策略差异可导致高达9%的召回率差距

  • 语义分块比固定长度准确率提升12-18%

  • 层次化分块 + 摘要索引提升检索精度25%

  • Contextual Retrieval降低召回失败率49%

  • 递归512-token分块在7种策略中排名第一(2026年2月基准)

分块策略的选择应基于实际语料和查询模式的评估数据,而非理论上的优越性。最有效的团队不是使用最复杂分块器的团队,而是测量、迭代、在数据证明收益时才增加复杂度的团队。
