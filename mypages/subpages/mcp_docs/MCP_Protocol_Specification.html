MCP (Model Context Protocol) 协议规范详解

版本：基于 MCP Specification 2025-11-25
来源：modelcontextprotocol.io 官方规范

一、概述

Model Context Protocol (MCP) 是由 Anthropic 于 2024 年 11 月推出的开放标准协议，旨在为 AI 应用（LLM）与外部数据源、工具和服务之间提供统一的集成接口。MCP 采用 JSON-RPC 2.0 作为通信协议，构建了一个有状态的会话协议，专注于上下文交换和采样协调。

MCP 的设计灵感来源于 Language Server Protocol (LSP)，但扩展了双向通信、动态发现和访问控制等能力。2025 年 12 月，Anthropic 将 MCP 捐赠给 Linux 基金会下的 Agentic AI Foundation (AAIF)，使其成为行业开放标准。

核心设计原则

  1. Servers should be extremely easy to build — Host 负责复杂的编排，Server 专注于单一、明确的能力

  2. Servers should be highly composable — 每个 Server 独立提供功能，多个 Server 可无缝组合

  3. Servers should not be able to read the whole conversation, nor "see into" other servers — Server 只能接收必要的上下文信息，完整对话历史保留在 Host 中

  4. Features can be added to servers and clients progressively — 核心协议提供最小功能集，额外能力可通过协商逐步添加，保持向后兼容

二、架构组件 (Architecture)

MCP 采用 Host-Client-Server 三层架构，其中每个 Host 可以运行多个 Client 实例。

┌─────────────────────────────────────────┐
│              Host (宿主应用)              │
│  ┌─────────┐    ┌─────────┐            │
│  │ Client 1│◄──►│ Server 1│ (文件系统)  │
│  └─────────┘    └─────────┘            │
│  ┌─────────┐    ┌─────────┐            │
│  │ Client 2│◄──►│ Server 2│ (数据库)    │
│  └─────────┘    └─────────┘            │
│  ┌─────────┐    ┌─────────┐            │
│  │ Client 3│◄──►│ Server 3│ (API 网关)  │
│  └─────────┘    └─────────┘            │
└─────────────────────────────────────────┘

2.1 Host (宿主)

Host 是 AI 应用本身（如 Claude Desktop、ChatGPT、VS Code with Copilot 等），作为容器和协调者：

  • 创建和管理多个 Client 实例

  • 控制 Client 的连接权限和生命周期

  • 执行安全策略和用户同意要求

  • 处理用户授权决策

  • 协调 AI/LLM 集成和采样（Sampling）

  • 管理跨 Client 的上下文聚合

Host 是"餐厅经理"，负责接收请求、决定调用哪些"厨房工作站"、协调最终响应。

2.2 Client (客户端)

每个 Client 由 Host 创建，与特定 Server 维持 1:1 的隔离连接：

  • 建立与 Server 的有状态会话（Stateful Session）

  • 处理协议协商和能力交换（Capability Exchange）

  • 双向路由协议消息（JSON-RPC 请求/响应/通知）

  • 管理订阅和通知（Subscriptions & Notifications）

  • 维护 Server 之间的安全边界

Client 是"服务员"，负责在 Host 和特定 Server 之间传递消息，确保不同 Server 之间的隔离。

2.3 Server (服务端)

Server 是提供专门化上下文和能力的服务进程：

  • 暴露 Resource、Tool 和 Prompt 等 MCP 原语

  • 独立运行，职责聚焦单一领域

  • 通过 Client 接口请求采样（Sampling）

  • 遵守安全约束

  • 可作为本地进程（STDIO）或远程服务（HTTP/SSE）运行

Server 是"厨房工作站"（如烧烤站、备餐站、甜品站），每个站点有特定能力，但都说同一种语言（MCP 协议）。

三、核心原语 (Primitives)

MCP 定义了三类服务端原语（Server-side Primitives）和三类客户端原语（Client-side Primitives）。

3.1 Server 端原语

3.1.1 Tool (工具)

定义：Tool 是 Server 暴露的可执行函数，允许语言模型调用以与外部系统交互（如查询数据库、调用 API、执行计算）。

交互模型：Tool 是 model-controlled（模型控制） 的，即语言模型可以基于上下文理解自动发现和调用工具。但出于安全考虑，实现中应当始终保留人工确认环节（human in the loop）。

能力声明：

xxxxxxxxxx
{
  "capabilities": {
    "tools": {
      "listChanged": true
    }
  }
}

Tool 定义结构：

示例 Tool 定义：

xxxxxxxxxx
{
  "name": "get_weather",
  "title": "Weather Information Provider",
  "description": "Get current weather information for a location",
  "inputSchema": {
    "type": "object",
    "properties": {
      "location": {
        "type": "string",
        "description": "City name or zip code"
      }
    },
    "required": ["location"]
  },
  "outputSchema": {
    "type": "object",
    "properties": {
      "temperature": { "type": "number" },
      "conditions": { "type": "string" }
    }
  }
}

调用流程：

  1. 发现：Client 发送 tools/list 请求获取可用工具列表

  2. 调用：Client 发送 tools/call 请求，携带工具名和参数

  3. 响应：Server 返回执行结果，包含内容数组和错误标志

Tool 结果内容类型：

  • text — 文本内容

  • image — Base64 编码的图片

  • audio — Base64 编码的音频

  • resource_link — 指向 Resource 的链接

  • resource — 嵌入的 Resource 内容

  • structuredContent — 结构化 JSON 输出（需同时提供文本序列化版本以保持兼容）

错误处理：

  • Protocol Errors：标准 JSON-RPC 错误（如未知工具、格式错误请求）

  • Tool Execution Errors：isError: true 的结果（如 API 失败、输入验证错误、业务逻辑错误）

3.1.2 Resource (资源)

定义：Resource 是 Server 暴露的只读数据源，通过 URI 寻址，为语言模型提供上下文信息（如文件内容、数据库记录、应用特定信息）。

交互模型：Resource 是 application-driven（应用驱动） 的，Host 应用决定如何根据需要将资源纳入上下文。可通过 UI 树/列表展示、搜索过滤、或基于启发式自动包含。

能力声明：

xxxxxxxxxx
{
  "capabilities": {
    "resources": {
      "subscribe": true,
      "listChanged": true
    }
  }
}

  • subscribe：Client 可订阅单个资源变更通知

  • listChanged：Server 在资源列表变化时发送通知

Resource 定义结构：

Resource 内容类型：

  • Text Content：{ "type": "text", "text": "..." }

  • Binary Content：{ "type": "blob", "blob": "base64..." }

Resource 模板 (Templates)： 允许 Server 暴露参数化资源，使用 URI Template 语法。Client 可通过自动补全 API 填充参数。

xxxxxxxxxx
{
  "resourceTemplates": [
    {
      "uriTemplate": "file:///{path}",
      "name": "Project Files",
      "description": "Access files in the project directory",
      "mimeType": "application/octet-stream"
    }
  ]
}

标准 URI Schemes：

  • https:// — Web 资源（仅当 Client 可直接获取时使用）

  • file:// — 类文件系统资源（无需映射到物理文件系统）

  • git:// — Git 版本控制集成

  • 自定义 Scheme — 必须符合 RFC 3986

Annotations（注解）：

  • audience：目标受众（["user"]、["assistant"] 或 ["user", "assistant"]）

  • priority：重要性（0.0 到 1.0，1.0 表示最重要）

  • lastModified：ISO 8601 格式最后修改时间

3.1.3 Prompt (提示模板)

定义：Prompt 是 Server 暴露的可复用提示模板，提供与语言模型交互的结构化消息和指令。

交互模型：Prompt 是 user-controlled（用户控制） 的，通过用户界面显式选择触发（如斜杠命令 /git）。

能力声明：

xxxxxxxxxx
{
  "capabilities": {
    "prompts": {
      "listChanged": true
    }
  }
}

Prompt 定义结构：

Prompt 消息结构 (PromptMessage)：

  • role："user" 或 "assistant"，表示发言者

  • content：支持以下类型：

    • text — 纯文本

    • image — Base64 编码图片（需 MIME 类型）

    • audio — Base64 编码音频（需 MIME 类型）

    • resource — 嵌入的 Resource 内容

示例 Prompt 定义：

xxxxxxxxxx
{
  "name": "code_review",
  "title": "Request Code Review",
  "description": "Asks the LLM to analyze code quality and suggest improvements",
  "arguments": [
    {
      "name": "code",
      "description": "The code to review",
      "required": true
    }
  ]
}

获取 Prompt 响应示例：

xxxxxxxxxx
{
  "description": "Code review prompt",
  "messages": [
    {
      "role": "user",
      "content": {
        "type": "text",
        "text": "Please review this Python code:
def hello():
    print('world')"
      }
    }
  ]
}

3.2 Client 端原语

3.2.1 Roots (根目录)

定义：Roots 是 Client 定义的文件系统边界，指定 Server 可以访问的目录和文件范围。

用途：确保 Server 在特定项目范围内操作（如 IDE 暴露当前项目目录），增强安全性和效率。支持动态更新，Client 可在根目录变化时通知 Server。

3.2.2 Sampling (采样)

定义：Sampling 允许 Server 通过 Client 接口请求 Host LLM 进行文本生成或推理。

用途：Server 可在任务中途暂停，向 Client 的 LLM 提出澄清问题或请求生成内容，支持真正的协作式工作流。这无需外部 API 密钥或临时通道，在同一会话内完成。

能力要求：Client 必须在初始化时声明 sampling 能力。

3.2.3 Elicitation (诱导/请求)

定义：Elicitation 允许 Server 请求用户输入或引导用户交互。

用途：当 Server 需要额外信息或用户确认时，通过 Client 向用户发起请求。URL 模式 Elicitation 可将敏感交互（如 API 密钥收集、第三方授权）重定向到 Server 托管的安全 URL，避免敏感数据通过 Client 传输。

四、会话生命周期 (Session Lifecycle)

MCP 定义了严格的四阶段生命周期：

4.1 初始化阶段 (Initialization)

  1. Client 发送 initialize 请求，包含：

    • 支持的协议版本

    • Client 能力声明（sampling、elicitation、roots 等）

    • Client 实现元数据

  2. Server 响应，包含：

    • 匹配或兼容的协议版本

    • Server 能力声明（prompts、tools、resources 等）

    • Server 元数据

  3. Client 发送 initialized 通知确认就绪

  4. 双方能力协商完成，后续操作只能在协商范围内进行

4.2 运行阶段 (Operation)

  • 双方根据协商的能力和协议版本交换请求、通知和响应

  • 支持双向消息流：Client 可调用 tools/list、resources/read 等；Server 可发起 sampling 或 elicitation 请求

  • 禁止调用未在初始化中协商的功能

4.3 关闭阶段 (Shutdown)

  • 无需特定协议消息，Client 或 Server 关闭底层传输连接即可

  • 实现应强制执行请求超时和健壮的错误处理

五、能力协商 (Capability Negotiation)

MCP 使用基于能力的协商系统，Client 和 Server 在初始化时显式声明支持的功能。

Server 能力：

  • resources：资源暴露（含 subscribe、listChanged 子能力）

  • tools：工具支持（含 listChanged 子能力）

  • prompts：提示模板（含 listChanged 子能力）

  • logging：日志级别控制

  • completion：参数自动补全

Client 能力：

  • sampling：支持 Server 请求 LLM 采样

  • roots：支持文件系统根目录暴露

  • notification：支持各类通知处理

协商规则：

  • 实现的功能必须在能力中广告

  • 发送资源订阅通知需要 Server 声明 subscribe 支持

  • 工具调用需要 Server 声明 tools 能力

  • 采样需要 Client 声明 sampling 支持

六、传输层 (Transport)

MCP 定义了两种主要传输机制，所有传输都使用 UTF-8 编码的 JSON-RPC 2.0 消息格式。

6.1 STDIO (标准输入输出)

  • 使用操作系统的标准输入/输出流

  • 适用于同一机器上的本地进程间通信

  • 性能最佳（无网络开销）

  • 是本地集成和原型开发的首选

6.2 Streamable HTTP

  • 使用 HTTP POST 和 GET 发送消息

  • 通过 Server-Sent Events (SSE) 流式传输实时响应

  • 支持多种 HTTP 认证选项（Bearer Token、API Key、自定义 Header）

  • 推荐 OAuth 2.1 进行授权

  • 适用于远程连接和云端部署

  • 支持长轮询（Polling）机制，允许 Server 关闭连接后 Client 通过事件 ID 重新连接

6.3 授权 (Authorization)

MCP 在 HTTP 传输层嵌入 OAuth 2.1 子集：

  • Client 作为 OAuth 客户端，向授权服务器请求访问令牌

  • 使用 PKCE 保护公共客户端（如 IDE 插件）

  • 支持基于 Scope 的细粒度授权（如 tools.read、tools.execute、resources.fs:read）

  • 支持增量 Scope 同意（Incremental Scope Consent），遵循最小权限原则

  • 支持 OAuth Client ID Metadata Documents (CIMDs) 作为动态客户端注册的替代方案

  • STDIO 传输应使用环境变量获取凭证

七、安全考量

7.1 Server 安全要求

  • 必须验证所有工具输入

  • 必须实现适当的访问控制

  • 应当对工具调用进行速率限制

  • 必须清理工具输出

  • 必须验证所有资源 URI

  • 应当对敏感资源实施访问控制

  • 必须正确编码二进制数据

  • 应当在操作前检查资源权限

  • 应当验证提示参数以防止注入攻击

7.2 Client 安全要求

  • 应当在敏感操作前提示用户确认

  • 应当在调用 Server 前向用户展示工具输入，防止数据泄露

  • 应当在传递给 LLM 前验证工具结果

  • 应当为工具调用实现超时机制

  • 应当记录工具使用日志以供审计

  • 必须将工具注解视为不可信（除非来自可信 Server）

7.3 架构安全原则

  • 隔离性：每个 Client-Server 连接维持独立会话，Server 无法读取完整对话或"窥视"其他 Server

  • 最小权限：Host 控制连接权限，Server 只能访问协商范围内的资源

  • 双向可控：Server 可请求采样和用户输入，但 Host 保留最终决策权

  • 审计追踪：所有工具调用、资源访问和采样请求都可关联到特定用户和会话

九、版本与演进

  • 2024-11 — Anthropic 首次发布 MCP

  • 2025-03 — OpenAI 官方采纳 MCP

  • 2025-11-25 — 当前规范版本（MCP Specification 2025-11-25）

  • 2026-03 — Microsoft 发布 MCP C# SDK v1.0，支持最新规范

主要演进特性：

  • 增强的授权服务器发现（三种元数据暴露方式）

  • 工具/资源/提示的图标支持

  • 增量 Scope 同意机制

  • URL 模式 Elicitation（敏感交互重定向）

  • 采样中的工具调用支持

  • 长轮询和 SSE 流存储

  • 实验性 Task 支持（持久状态跟踪）

十、总结

MCP 协议通过标准化的 JSON-RPC 接口，将 AI 应用与外部工具、数据和服务的集成从"N×M 问题"简化为"即插即用"的生态系统。其核心架构（Host-Client-Server）确保了安全性、模块化和可组合性，而三类服务端原语（Tool、Resource、Prompt）和三类客户端原语（Roots、Sampling、Elicitation）共同构成了丰富的交互能力。随着主要 AI 平台（Anthropic、OpenAI、Google、Microsoft）的采纳和 Linux 基金会的标准化推动，MCP 正成为 AI 原生应用的基础连接协议。
