1. MCP 安全架构概述

MCP 服务器位于 AI Agent、工具和数据系统之间的执行路径上，这一位置使其成为整个系统的控制平面。如果 MCP 服务器被攻击者攻破，他们将间接获得对工具执行、数据访问和系统行为的控制权。

MCP 安全设计必须像对待数据库引擎、API 网关和身份提供商一样严格。大多数 MCP 安全失败并非源于协议本身的弱点，而是来自：

  • 过度宽泛的权限

  • 弱身份执行

  • 缺失的运行时隔离

  • 不足的审计可见性

MCP 安全遵循传统分布式系统安全原则：先执行身份认证，再践行最小权限，隔离执行环境，记录一切操作。

2. 工具授权模型

2.1 核心授权问题

当 Agent 调用 MCP 服务器上的工具时，服务器必须回答两个问题：

  1. 这个客户端是否有权调用此工具？ —— 由 MCP 授权机制（OAuth 2.1 + scopes）回答

  2. 这次具体的调用（含具体参数）是否获得了指定人员的批准？ —— 需要在 MCP 之上额外实现

对于只读数据查询、搜索、摘要等低风险操作，问题 (1) 已足够。但对于涉及资金、基础设施变更、数据导出或不可逆操作的工具，问题 (2) 的答案是不可或缺的。

2.3 能力建模 (Capability Modeling)

每个 MCP 工具必须暴露狭窄且明确的能力边界。工具绝不能充当通用执行端点，因为宽泛的执行面会增加攻击影响面。

每个工具在注册前必须声明：

  • 操作类型：读 / 写 / 管理

  • 数据范围：租户级、Schema 级或数据集级限制

  • 资源限制：每工具的 CPU、内存和执行时间上限

  • 外部副作用：网络调用或外部系统写入的显式声明

能力定义必须在 MCP 服务器边界处强制执行，而非在工具代码内部。工具应假设权限检查已完成，不应独立做出信任决策。

2.4 工具范围检查清单

2.5 反模式：万能工具 (Omnibus Tool)

最典型的审计异味是名为 execute、query、run 或 action 的工具，只接受单个自由格式字符串参数。这种模式将工具目录缩减为一个具有最大爆炸半径的工具，使得：

  • 按工具授权变得不可能

  • 审计日志无法解释

  • 攻击面最大化

正确做法：拆分为狭窄工具，即使目录规模会增大。

3. 沙箱执行机制

3.1 为什么需要沙箱

MCP 服务器经常按照 AI Agent 的指示执行代码或命令，这使其面临多种风险：

  • 提示注入导致执行恶意命令

  • 工具返回的不可信数据重新进入 Agent 上下文

  • 单个工具被攻破后横向移动

如果没有沙箱或最小权限隔离，机密性风险是巨大的。

3.2 沙箱实现层级

3.3 沙箱核心要求

  • 无互联网访问：每个任务在隔离容器中运行，防止跨任务干扰

  • 预填充 Mock 服务：使用预设夹具启动 Mock 服务，注入随机 API 错误以测试鲁棒性

  • 路径映射：自动映射可执行路径、配置路径和工作区路径，确保工具在容器内正常运行

  • 资源限制：每工具的 CPU、内存和执行时间上限，防止资源耗尽或拒绝服务

  • 网络分段：将 MCP 服务器隔离在专用网络段中，配置适当的防火墙规则

4. 审计日志体系

4.1 审计日志的必要性

没有审计可见性的安全在事件发生时必然失败。每次 MCP 工具调用都必须生成结构化审计记录。

审计日志不仅是技术需求，更是合规需求。仅记录工具名称和时间戳的日志满足狭窄的技术要求；而记录用户身份、Agent 身份、完整请求上下文、应用策略和输出内容的结构化日志则满足 SOC 2、HIPAA 和 GDPR 要求。

4.2 审计日志必须包含的字段

4.3 PII 脱敏要求

审计日志中必须对敏感信息进行脱敏处理。详细的 JSON-RPC 日志会逐字捕获参数值 —— 电子邮件地址、作为参数传递的 API 密钥、客户姓名。

脱敏原则：

  • 在结构化日志层进行脱敏，而非在日志接收端

  • 绝不在后处理阶段脱敏

  • 使用标记化替换（如 EMAIL_REDACTED、API_KEY_REDACTED）

4.4 日志保留与合规

  • 日志应保留在自有环境中，而非第三方 SaaS 系统

  • 与 SIEM 平台集成，关联 MCP 事件与身份行为和网络流量

  • 支持实时查询和按需导出

  • 保留期限应符合行业合规要求（如金融行业通常要求 7 年）

4.5 异常检测

审计日志应支持检测以下异常模式：

  • 不寻常的工具访问序列

  • 权限提升尝试

  • 数据外泄指标

  • 隐形 Agent 活动（LLM 处理但不向用户显示的操作）

  • 特定工具的频率突增（如从正常速率突然飙升到每秒数千次请求）

5.2 信任模型实施要点

  • 数字签名：工具必须由已知实体签名，客户端验证工具代码或定义是否匹配已知良好哈希

  • 版本锁定：锁定特定 MCP 服务器版本，任何变更触发管理员告警

  • 集中式能力注册表：控制工具暴露和权限，防止未授权工具注册

  • 供应链监控：跟踪版本、监控开源工具的提交历史，建立内部批准的 MCP 连接器注册表

6. 安全成熟度模型

6.1 Level 1 — 基础阶段

特征：

  • 仅基于令牌的认证

  • 系统范围内的宽泛工具权限

  • 无运行时隔离或沙箱

  • 有限或无审计可见性

  • Token 泄露时爆炸半径极大

适用场景：原型和早期内部部署

6.2 Level 2 — 生产就绪

特征：

  • 令牌 + 能力强制执行

  • 容器级运行时隔离

  • 基本的工具执行审计日志

  • 通过限定权限减少爆炸半径

  • 仍易受供应链和身份欺骗风险

适用场景：处理内部企业工作负载的生产系统

6.3 Level 3 — 企业级成熟

特征：

  • mTLS + 基于令牌的用户和租户范围授权

  • 工具构件签名和验证

  • 集中式能力注册表

  • 工具全生命周期的完整审计可见性

  • 有效防止网络内部横向移动

适用场景：受监管环境和大规模多租户部署

8. 最佳实践与实施建议

8.1 架构层面

  1. 部署集中式 MCP 网关：作为所有 MCP 通信的代理，强制执行已批准 MCP 服务器的白名单、集中访问控制和审计、检查所有工具调用

  2. 实施最小权限访问：将用户角色映射到具体工具能力，使用能力级权限范围替代宽泛范围 Token

  3. 网络隔离：将 MCP 服务器隔离在专用网络段，配置防火墙规则限制爆炸半径

8.2 开发阶段

  1. 静态应用安全测试 (SAST)：在构建流水线中集成 SAST

  2. 软件成分分析 (SCA)：识别依赖中的漏洞

  3. 安全编码实践：特别关注输入验证和命令执行

  4. 组件签名：对所有 MCP 组件进行数字签名确保完整性

8.3 部署阶段

  1. 沙箱环境运行：以最小所需权限运行 MCP 服务器

  2. 全面日志记录：记录所有 MCP 服务器操作

  3. 定期漏洞管理：对 MCP 组件进行定期漏洞扫描

  4. 网络分段：限制被攻破服务器的爆炸半径

8.4 运营阶段

  1. 行为监控：监控 MCP 服务器的异常活动

  2. 敏感操作确认：对敏感操作实施用户确认

  3. 定期审计：每季度重新审计，与 SOC2 控制对齐

  4. 事件响应：制定专门针对 MCP 相关安全事件的响应程序
