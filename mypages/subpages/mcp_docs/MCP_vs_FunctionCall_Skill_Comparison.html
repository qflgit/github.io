1. 核心概念速览

1.1 Function Calling

定义：Function Calling 是 LLM 的内置能力，让模型能够生成结构化 JSON 输出，表达"我要调用这个函数、参数是这些"。

本质：模型与函数之间的单次调用格式规范，是 AI Agent 触发外部动作的最底层"语言"。

典型实现：OpenAI Chat Completions API 的 tools 参数、Anthropic Messages API 的 tool_use。

1.2 MCP (Model Context Protocol)

定义：MCP 是一个开放标准协议，定义了 AI 客户端与工具服务之间如何发现、连接和调用工具。

本质：在 Function Calling 之上做工具标准化封装，让工具从"应用内的代码片段"变成"独立的标准化服务"。

治理：2025 年 12 月由 Anthropic 捐赠给 Linux 基金会旗下的 Agentic AI Foundation (AAIF)。

1.3 Skill

定义：Skill 是将使用工具完成特定任务的知识和流程封装成的可复用模块。

本质：在 MCP 之上的流程编排层，定义"用这些工具按什么流程完成任务"。

典型实现：Claude Code 的 TaskMaster、各类 Agent 框架中的 Skill 定义。

2. 三者层级关系

2.1 架构分层

三者不是并列的竞争方案，而是从底到顶的三层架构：

┌─────────────────────────────────────────────┐
│  Skill 层                                    │
│  (流程编排、知识封装、任务模板)                │
│  Agent 按 Skill 定义的标准流程执行任务         │
├─────────────────────────────────────────────┤
│  MCP 层                                      │
│  (工具标准化、服务发现、跨模型复用)            │
│  Client 连接 Server 自动发现可用工具           │
├─────────────────────────────────────────────┤
│  Function Calling 层                          │
│  (模型触发调用的底层协议)                      │
│  模型输出 tool_calls JSON 触发具体调用         │
└─────────────────────────────────────────────┘

2.2 通信角色

2.3 完整调用链

以一个"分析销售数据并生成报告"的任务为例：

  1. Skill 层：Agent 发现"数据分析报告"Skill，加载 SKILL.md 中的三步流程（取数据 → 做分析 → 写报告）

  2. MCP 层：Agent 的 MCP Client 已连接数据库 Server 和 Python 执行器 Server，自动知道 query_database 和 run_python 可用

  3. Function Calling 层：模型判断需要查数据库，输出 tool_calls: query_database(sql="...")，MCP Client 路由到数据库 Server 执行

3.1 MCP vs Function Calling 全面对比

3.2 MCP vs Function Calling 核心差异

架构差异：

  • Function Calling 在模型请求-响应周期内运行，工具逻辑嵌入应用

  • MCP 创建独立层，工具在独立 Server 上运行，通过标准化协议通信

可扩展性差异：

  • Function Calling 每次请求发送所有工具 Schema，开销随工具数线性增长

  • MCP 按需加载，可扩展到数百工具而不增加 Prompt 大小

供应商可移植性：

  • OpenAI、Anthropic、Google 的 Function Calling 格式各不相同，切换需重写 Schema

  • MCP 是供应商无关的，一个 Server 可被任何兼容 Client 使用

安全差异：

  • Function Calling 将 API Key 存储在 Agent 运行时

  • MCP 将凭据隔离在 Server 端，降低合规风险

4. 架构差异详解

4.1 Function Calling 的执行循环

xxxxxxxxxx
应用进程内：
┌──────────────────────────────────────────┐
│  1. 定义工具 JSON Schema                  │
│  2. 将 Schema 放入 API 请求 tools 参数     │
│  3. 模型返回 tool_calls JSON               │
│  4. 应用读取响应，本地执行函数              │
│  5. 将结果以 tool 消息形式回传模型          │
└──────────────────────────────────────────┘

所有环节在一个进程内完成：工具 Schema、执行逻辑、凭据、错误处理都内嵌在应用中。

4.2 MCP 的客户端-服务器模型

xxxxxxxxxx
┌─────────────┐      JSON-RPC 2.0       ┌─────────────┐
│  MCP Host   │  ←──────────────────→  │  MCP Server │
│  (AI 应用)   │   (stdio / SSE / HTTP)  │  (工具服务)  │
│             │                         │             │
│  MCP Client │  ── tools/list ──────→  │  工具发现    │
│  (连接管理)  │  ←─ 工具列表 ─────────  │             │
│             │  ── tools/call ──────→  │  工具执行    │
│             │  ←─ 执行结果 ─────────  │             │
└─────────────┘                         └─────────────┘

三个组件参与：

  • MCP Host：AI 应用（如 Claude Desktop、Cursor、VS Code）

  • MCP Client：维护与 Server 的连接

  • MCP Server：独立进程，暴露 tools、resources、prompts

4.3 Skill 的编排模型

xxxxxxxxxx
Agent 启动时扫描 Skill 列表
         ↓
用户提出任务 → Agent 匹配相关 Skill
         ↓
加载 SKILL.md（执行指令、脚本、模板）
         ↓
按 Skill 定义流程分步执行
         ↓
每步需要工具时 → 通过 MCP 发现 → 通过 Function Calling 触发

Skill 内部可能涉及多个步骤、调用多个 MCP 工具，是一个完整的"操作手册"。

6.1 迁移前提评估

6.2 四阶段迁移路径

Phase 1: 双轨运行 (第 1-2 周)

  • 保留现有 Function Calling 集成正常运行

  • 在旁路部署 MCP Gateway 或首个 MCP Server

  • 选择 1-2 个非关键工具作为试点迁移

  • 验证 MCP Client 与现有系统的兼容性

xxxxxxxxxx
# 双轨运行示例：同时支持两种模式
async def call_tool(tool_name, params):
    if tool_name in mcp_tools:
        return await mcp_client.call(tool_name, params)
    else:
        return await legacy_function_call(tool_name, params)

Phase 2: MCP Gateway 部署 (第 3-4 周)

  • 部署 MCP Gateway（如 IBM ContextForge、MetaMCP）

  • 将新集成统一路由到 MCP 层

  • 在 Gateway 层实现统一的认证、审计和访问控制

  • 保持 Function Calling 作为关键路径的 Fallback

Phase 3: 渐进式迁移 (第 2 个月)

  • 逐个迁移现有工具到 MCP Server

  • 每次迁移一个工具后立即测试

  • 维护 Function Calling 的 Fallback 路径

  • 记录迁移过程中的问题和解决方案

迁移单个工具的步骤：

  1. 将工具逻辑从应用内提取到独立进程

  2. 用 MCP SDK 包装为 MCP Server（stdio 或 SSE 模式）

  3. 在 MCP Client 中注册新 Server

  4. 验证工具发现、调用和返回结果

  5. 更新应用代码，从直接调用改为 MCP Client 调用

  6. 运行回归测试

  7. 下线旧 Function Calling 实现

Phase 4: 全面采用 (第 3 个月)

  • 停用遗留 Function Calling 集成

  • 启用 MCP-only 特性（如 Resources、Prompts、动态发现）

  • 建立内部 MCP Server 注册表

  • 制定 MCP Server 开发和发布规范

7. 常见误区

误区 1：将三者视为竞争方案

错误认知：Function Calling、MCP、Skill 是三个平行的竞争方案，选一个即可。

正确理解：三者是互补的三层架构。Function Calling 是底层语言，MCP 是中间层协议，Skill 是上层流程封装。完整的 Agent 系统通常三层都需要。

误区 2：认为 MCP 会取代 Function Calling

错误认知：MCP 是 Function Calling 的替代品。

正确理解：MCP 内部仍然使用 Function Calling。模型生成结构化请求的方式不变，MCP 只是标准化了请求的路由和执行。两者是"基础设施 vs 底层机制"的关系。

误区 3：认为 Function Calling 已被弃用

错误认知：MCP 崛起意味着 OpenAI Function Calling 正在被淘汰。

正确理解：OpenAI 持续投资 Function Calling，增加了 strict 模式、改进了并行调用可靠性、更深地集成到 Assistants API。它仍是全球最广泛使用的 LLM API 工具调用机制。

误区 4：低估 MCP Server 的安全风险

错误认知：MCP Server 只是配置文件，无需关注安全。

正确理解：每个 MCP Server 都是网络进程，有自己的攻击面。需要认证、输入校验、TLS、沙箱隔离。跳过这些步骤会使工具调用 Agent 成为系统中最薄弱的环节。

误区 5：过度设计工具 Schema

错误认知：工具 Schema 越全面越好。

正确理解：无论使用 Function Calling 还是 MCP，小而聚焦的工具配合精确的 Schema 才能产生更好的模型行为。大而全的工具 Schema 会增加模型调用错误工具或传入畸形参数的概率。

误区 6：选择 MCP 仅因为它"更现代"

错误认知：MCP 更新、更有势头，所以应该选它。

正确理解："更新"不是使用场景。如果没有具体的可移植性或多模型需求，维护 MCP Server 基础设施只会增加复杂度而没有实际收益。选择 MCP 需要有具体理由。

8.2 组合使用策略

策略 1：Function Calling + MCP 并存

  • Function Calling 用于 OpenAI-only 生产负载

  • MCP 用于新 Agent 原型和多模型实验

  • 两者在组合层面不互斥

策略 2：MCP + Skill 完整栈

  • MCP 提供工具基础设施

  • Skill 提供流程编排

  • Function Calling 作为底层触发机制（透明使用）

策略 3：渐进式演进

  • 第 1 阶段：纯 Function Calling（验证业务价值）

  • 第 2 阶段：Function Calling + 少量 MCP Server（试点）

  • 第 3 阶段：MCP Gateway + 全面迁移（规模化）

  • 第 4 阶段：Skill 层 + MCP 基础设施（成熟治理）
